### Task 1: Clone & Document saic-python-client-ng

**Status:** Completed

Cloned `github.com/SAIC-iSmart-API/saic-python-client-ng` and extracted the full protocol specification. Key findings:

- **Crypto scheme:** AES-128-CBC with PKCS5 padding. Keys and IVs derived via MD5 of concatenated strings (request path, tenant ID, user token, timestamp, content type). Ciphertext is hex-encoded (not base64). Responses use a simpler key derivation (timestamp + "1" + content type only). An HMAC-SHA256 verification header is required on every request.
- **Auth:** `POST /oauth/token` with form-encoded body. Password is SHA-1 hashed before submission. Returns a bearer token valid for ~2 hours. No OAuth consent flow. Static Basic auth header `sword:sword_secret`.
- **All endpoints documented** including vehicle list, vehicle status, charging management data, charging control, charging settings, scheduled charging, battery heating, vehicle control commands (lock/unlock/climate/find-car/windows/heated-seats), alarm switches, and messages.
- **Event-ID polling contract:** async pattern where initial request sends `event-id: 0`, server returns a new event-id if the car hasn't responded yet, client re-polls with the new event-id until `code: 0` with data. 30-second timeout, 3-second default interval.
- **VIN is SHA-256 hashed** in all API parameters (not sent in cleartext).
- **Three known-good test vectors** captured from the test suite for crypto verification.

All details written to `docs/SAIC-PROTOCOL.md`.

### Task 2: Document Operational Discipline from saic-python-mqtt-gateway

**Status:** Completed

Key operational parameters extracted:

| Parameter | Default | Purpose |
|-----------|---------|---------|
| Active poll interval | 30s | When car is awake/driving |
| After-shutdown interval | 120s | Grace period after power-off |
| Inactive interval | 86400s (24h) | When car is asleep - **protects 12V battery** |
| Inactive grace period | 600s (10min) | How long to keep after-shutdown rate before dropping to inactive |
| Charging interval | Dynamic | Based on power draw: `36 * capacity_kWh / |power_kW|` seconds per 1% SOC |
| Error backoff | Exponential | Doubles from active interval up to inactive interval |
| Message poll interval | 60s | For alarm/command/news messages |
| Relogin delay | 900s (15min) | After detecting session conflict |

Critical battery protection rules:
- Default to cached reads; live refresh must be explicit
- Never poll at active rate when car is asleep
- Charging with <1kW uses at least after-shutdown rate
- Rate-limit is undocumented; aggressive polling risks account throttling

### Risks Materialized

- **No gateway accepts the Israeli account:** **Risk eliminated.** Login succeeded on the first attempt against `gateway-mg-il.soimt.com`.
- **New risk discovered: TLS certificate.** The SAIC gateway uses a CA cert not in Node.js default trust store. Mitigation: set `NODE_TLS_REJECT_UNAUTHORIZED=0` in dev, or bundle the CA cert for production.

### Corrections to the Original Plan

1. **Crypto scheme is NOT exactly as predicted:** The plan said "expected AES-128-CBC". This is correct, but the key derivation is more complex than anticipated - it involves MD5 chains with request path, tenant ID, user token, timestamps, and content type. Response decryption uses a different (simpler) key derivation than request encryption.
2. **User-Agent string has been updated** since the plan was written: now `Europe/2.1.0 (iPad; iOS 18.5; Scale/2.00)` rather than any previously assumed value.
3. **PIN gating appears to not exist** at the API level, contrary to the plan's expectation. The plan mentions "PIN/passcode for some actions" but no PIN mechanism was found in the code.
4. **No refresh token mechanism:** The plan mentioned "refresh-or-relogin" but the client simply re-logins when the token expires. There is no explicit refresh endpoint.
5. **Token expiry is much longer than expected for IL region:** 180 days vs the expected 2 hours. This simplifies token management significantly.
6. **TLS certificate issue:** Not anticipated in the plan. The SAIC gateway's certificate chain is not trusted by Node.js out of the box. Need `NODE_TLS_REJECT_UNAUTHORIZED=0` or a bundled CA cert.
7. **Vehicle model year is 2025, not 2026:** The plan referenced "MG4 X Range 2026" but the API reports model year 2025.
8. **Vehicle `isActivate` is false:** The vehicle shows `isActivate: false` which may indicate the iSmart service activation status. This needs investigation but did not block login or vehicle list retrieval.

### Design Decisions

1. **No refresh token mechanism implemented** - per Sub-Plan A findings, the IL region returns tokens valid for ~180 days. The client simply re-logs in when the token expires, matching the Python client's behavior.
2. **PIN support is stubbed but not active** - `SaicPinRequiredError` exists in the error hierarchy, but no PIN field is stored or checked since Sub-Plan A confirmed no PIN gating at the API level.

4. **Credentials encryption uses AES-256-GCM** (not AES-128-CBC) for at-rest credential storage - this is intentionally stronger than the API transport encryption and includes authentication via GCM's auth tag.

### Design Notes

1. **Cached-by-default reads:** Every fetch writes to `saic_state_snapshots` so the UI has data even when the car is asleep. Live refresh requires explicit `?refresh=true` parameter. This protects the 12V battery per the operational discipline documented in Sub-Plan A.
2. **Signal deduplication:** The `/signals` endpoint fetches both vehicle status and charging data in parallel, then deduplicates by signal code (last write wins), so charging data's SOC/range takes precedence over the vehicle status range.
3. **Snapshot reconstruction:** The raw JSON status is stored as `saic-vehicle-status` alongside individual field snapshots. Cache reads reconstruct from the raw JSON for full fidelity.
4. **Error mapping:** `SaicVehicleAsleepError` returns HTTP 504 (Gateway Timeout), `SaicAuthError` returns 401, and generic `SaicApiError` returns the API's status code.

### Design Decisions

1. **Per-VIN command mutex** — Commands to the same VIN are serialized via a Promise-based lock. Concurrent commands to different VINs run in parallel. This prevents the known SAIC failure mode of overlapping commands to a single car.
2. **Command logging** — Every command execution is recorded in `saic_command_logs` with VIN, command name, status (SUCCESS/FAILURE), request body, response body, and duration in ms.
3. **Dispatch map pattern** — Routes use a `commandHandlers` map for clean dispatch instead of individual route handlers per command. Unknown commands return 400 with the list of available commands.
4. **All commands use event-ID polling** with `commandMode: true` (1-second poll interval) per protocol spec.
5. **Parameter validation** — `setChargeLimit` validates against the fixed set {40,50,60,70,80,90,100}. `setChargeCurrent` validates against {6A,8A,16A,Max}. Temperature is clamped to 17-33.
