# Charging Statistics Feature for SAIC Dashboard

Add charging session tracking with energy efficiency statistics (kWh/100km) to the SAIC integration, using alarm-based auto-detection + manual fallback buttons, presented in a new "Statistics" sidebar page.

---

## Charge Detection Approach: Alarm Message Polling + Manual Buttons

### Investigation Summary

SAIC has no webhook/push API and no way to subscribe to events. The MQTT gateway (`saic-python-mqtt-gateway`) was considered but has a **dealbreaker**: the SAIC API is hostile to multi-session - running a separate Python gateway alongside this Node.js backend would cause constant authentication conflicts (each login invalidates the other's session).

### Chosen Approach: Two-Layer Detection

**Layer 1 - Automatic: Alarm Message Polling (always on)**

The SAIC API has two categories of endpoints:
- **Vehicle endpoints** (`/vehicle/status`, `/vehicle/charging/mgmtData`) - use event-ID polling which **wakes the T-BOX** and drains 12V
- **Account endpoints** (`/message/list`, `/message/unreadCount`) - simple server-side queries that do **NOT wake the car**

The T-BOX pushes alarm messages to SAIC's cloud when events occur (including charging start/stop). Polling `/message/list?messageGroup=ALARM` every 60-120 seconds is completely safe - it queries data SAIC cloud already has, never contacts the car.

Flow:
1. Backend polls `/message/list?messageGroup=ALARM` every 60s (already implemented as `getMessages()`)
2. Tracks last-seen message ID to detect new messages
3. When a charging-related alarm is found → auto-creates/completes a charging session
4. Does a single live data fetch for SOC + odometer (safe: car is awake during charging)
5. Always on - no env var needed since it's 12V-safe

**Layer 2 - Manual Fallback: Dashboard Buttons**

"Log Charge Start" / "Log Charge Stop" buttons on the SAIC dashboard for:
- Cases where alarm messages are delayed or missing
- Manual override/correction
- First-time use before alarm format is validated

**Note**: The exact `messageType`/`title`/`content` format of charging alarm messages needs discovery. The alarm poller will log all alarm messages so we can identify the patterns. If charging alarms don't exist, the manual buttons remain the primary interface and the poller simply becomes a no-op for charging.

## Architecture Overview

### Data Model

The MG4 X Range has a **77 kWh** battery capacity.

**Key calculation**: `battery_kwh = soc_percent * 0.77`

Between charges:
- `energy_used_kwh = previous_end_battery_kwh - current_start_battery_kwh`
- `distance_km = current_start_odometer - previous_end_odometer`
- `efficiency = (energy_used_kwh / distance_km) * 100` (kWh/100km)

After charging:
- `energy_added_kwh = end_battery_kwh - start_battery_kwh`

### New Database Table: `saic_charging_sessions`

```sql
CREATE TABLE IF NOT EXISTS saic_charging_sessions (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  vin TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'charging',  -- 'charging' | 'completed'
  start_time TEXT NOT NULL DEFAULT (datetime('now')),
  end_time TEXT,
  start_soc_pct REAL NOT NULL,            -- e.g. 25.5 (%)
  end_soc_pct REAL,                        -- e.g. 80.0 (%)
  start_battery_kwh REAL NOT NULL,         -- e.g. 19.635 (kWh)
  end_battery_kwh REAL,                    -- e.g. 61.6 (kWh)
  energy_added_kwh REAL,                   -- calculated on stop
  start_odometer_km REAL NOT NULL,         -- e.g. 1523.4
  end_odometer_km REAL,                    -- same at stop (shouldn't change during charge)
  distance_since_last_charge_km REAL,      -- km driven since previous session ended
  energy_used_since_last_charge_kwh REAL,  -- kWh used since previous session ended
  efficiency_kwh_per_100km REAL,           -- calculated: energy_used / distance * 100
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE INDEX IF NOT EXISTS idx_saic_charging_sessions_vin
ON saic_charging_sessions(vin, start_time);
```

### New Backend API Endpoints

| Method | Path | Description |
|--------|------|-------------|
| `POST` | `/api/saic/vehicles/:vin/charging-sessions/start` | Log charge start: live-fetches SOC + odometer, creates session |
| `POST` | `/api/saic/vehicles/:vin/charging-sessions/stop` | Log charge stop: live-fetches SOC, calculates stats, completes session |
| `GET` | `/api/saic/vehicles/:vin/charging-sessions` | List all sessions (paginated) |
| `GET` | `/api/saic/vehicles/:vin/charging-sessions/stats` | Aggregate statistics |
| `DELETE` | `/api/saic/vehicles/:vin/charging-sessions/:id` | Delete a session |

### Frontend Components

1. **Dashboard addition**: Two new buttons in the Battery & Charging card - "Log Charge Start" / "Log Charge Stop"
2. **New Statistics page** at `/saic/statistics`:
   - Summary card: total energy added, total distance tracked, average efficiency, session count
   - Per-session table with date, SOC before/after, energy added, distance driven, efficiency
   - Efficiency trend visualization (comparing efficiency between charges)
3. **New sidebar nav item**: "Statistics" with `bar_chart` icon, under the SAIC provider

## Risks & Considerations

1. **SOC precision**: SAIC reports SOC as `bmsPackSOCDsp * 0.1` (e.g., 805 = 80.5%). The kWh calculation `soc * 0.77` gives reasonable precision.

2. **Odometer during charging**: Should remain constant since the car is stationary. We record it at start and end for completeness.

3. **Distance between charges**: Calculated as `current_start_odometer - previous_end_odometer`. If the previous session's end odometer is null (e.g., first session), we skip the efficiency calculation for that ride.

4. **Active session guard**: Only one active session per VIN. Attempting to start when one is active returns an error. This prevents data corruption from double-clicks or duplicate alarm processing.

5. **Live data fetch on button click / alarm trigger**: Since the car is awake during charging, the live fetch to get current SOC/odometer is safe for the 12V battery. The existing `refreshLimiter` (6 per 5 min) applies.

6. **First session**: The first session won't have "distance since last charge" or "efficiency" data since there's no previous session to compare against. The UI should handle this gracefully.

7. **Alarm message format unknown**: We don't know the exact `messageType`/`title`/`content` for charging alarm messages. The poller will log all ALARM messages at DEBUG level to discover the format. If charging alarms don't exist in the SAIC cloud for the IL region, the manual buttons remain fully functional and the poller simply doesn't trigger sessions. The alarm detection patterns can be refined over time as we see real messages.

8. **SAIC session conflict**: The alarm poller uses the same SAIC session as the rest of the app (same `getMessages()` function, same token). No session conflict. The MQTT gateway was rejected specifically because it would create a second session.

9. **Alarm poller and SAIC account**: The poller requires a SAIC account to be connected. If no account is connected, the poller should silently skip (log at DEBUG level, not error).
