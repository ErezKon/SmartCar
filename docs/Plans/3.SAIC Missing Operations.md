### 1C. SmartCar Features with NO SAIC Equivalent

Answering the original question about SmartCar operations like mileage and webhooks:

| SmartCar Feature | SAIC Equivalent | Notes |
|------------------|----------------|-------|
| **Webhooks** (`/webhooks`, `/subscriptions`) | **None** | SAIC is poll-based only. No push/WebSocket/callback mechanism exists. The closest equivalent is polling at intervals (as the MQTT gateway does). |

| **Odometer as standalone endpoint** | **None** | Mileage is part of `vehicle/status` response, not a separate call. Already implemented via `normalizeVehicleStatus`. |

| **Firmware Version** | **None** | Not exposed. |
| **Drive Mode / Gear State** | **None** | Not in SAIC vehicle status. |
| **Surveillance** | **None** | Not applicable. |

**Key insight:** The SAIC API does NOT have webhooks or any push mechanism. However, it has several features SmartCar doesn't: window/sunroof remote control, heated steering wheel, front/rear defrosters as separate controls, charging cable lock, battery heating schedules, and alarm notification configuration.

## 3. Regarding "Mileage" and "Webhooks"

### Mileage
The SAIC API already provides mileage via `basicVehicleStatus.mileage` (total odometer), and we normalize it as `odometer-traveleddistance`. However, there are **three additional mileage-related fields** we're not extracting:
- `mileageOfTheDay` - Daily driving distance (resets daily)
- `mileageSinceLastCharge` - Distance since the last charge session
- `currentJourneyDistance` - Live trip odometer for the current journey

These are implemented in **Phase 1** above. There is no separate "get mileage" API call - all mileage data comes from the existing status/charging endpoints we already call.

### Webhooks
The SAIC iSmart API is **entirely poll-based**. There is no webhook, WebSocket, or push notification system. The SmartCar webhook system (`/webhooks`, `/subscriptions`) has no SAIC equivalent.

The community workaround (used by the MQTT gateway) is **scheduled polling** with smart intervals:
- Active vehicle: every 30s
- After shutdown: every 120s (grace period of ~10min)
- Inactive/sleeping: every 24h (to avoid draining 12V battery)
- During charging: dynamically computed from charging power

If we want "webhook-like" behavior, we could implement a **background poller** that pushes updates via Server-Sent Events (SSE) or stores them for client polling. This would be a separate plan item.

| Tyre Pressures | FL, FR, RL, RR | `diagnostics-tirepressure` |

### Root Cause 1 (Critical): Event-ID Polling Terminates Prematurely

**File:** `backend/src/saic/client.ts`, `singleRequest()` method (lines 187-210)

The SAIC API (Israeli gateway confirmed) returns an initial response of `{code: 0, message: "success"}` WITH an `event-id` response header. This means "request acknowledged, poll with this event-id for actual data." However, the TypeScript client only retries when `code != 0`:

```typescript
// Current code (line 187):
if (parsed.code !== 0) {
  if (respEventId) {
    throw new SaicRetryException(parsed.message, respEventId);
  }
}
return parsed;  // BUG: returns wrapper {code:0, message:"success"} as if it were vehicle data
```

The Python reference client (`saic-python-client-ng`) correctly retries in TWO cases:
1. `code != 0` with event-id (our code handles this)
2. Event-id in response headers but `data` field is absent (our code does NOT handle this)

**Evidence:** The Docker database snapshots (`saic_state_snapshots` table) contain `{"code":0,"message":"success"}` for both `saic-vehicle-status` and `saic-charging-data` fields. A live refresh (`GET /api/saic/vehicles/:vin/status?refresh=true`) returns `{"data":{"code":0,"message":"success"},"cached":false}` in ~1 second (no polling occurred).

**Impact:** ALL signals from BOTH `normalizeVehicleStatus` and `normalizeChargingData` are empty because `data.basicVehicleStatus` and `data.chrgMgmtData` are undefined on the `{code, message}` wrapper object.

**Fix required in `client.ts`:** After the `code !== 0` check, add a second check:

```typescript
// Also retry when code is 0 but data is missing and an event-id was provided
if (parsed.data === undefined && respEventId) {
  throw new SaicRetryException('Waiting for vehicle data', respEventId);
}
```

### Root Cause 3 (Medium): Silent Error Swallowing in Signals Route

**File:** `backend/src/routes/saic.routes.ts`, lines 253-256

```typescript
const [statusData, chargingData] = await Promise.all([
  getVehicleStatus(vin, refresh).catch(() => null),
  getChargingData(vin, refresh).catch(() => null),
]);
```

Both calls use `.catch(() => null)` which silently discards ALL errors (auth failures, network errors, database errors, TLS errors). The frontend receives `{"data":[],"count":0}` with no indication that anything went wrong. This made the bug in Root Cause 1 invisible - no error messages appeared anywhere.

**Fix required:** Log the error before returning null:

```typescript
getVehicleStatus(vin, refresh).catch(err => {
  logger.warn(`Failed to get vehicle status: ${err.message}`);
  return null;
}),
```

### Root Cause 4 (Low): No Data Validation Before Persistence

**File:** `backend/src/saic/vehicles.ts`, lines 77-79 and 112-113

Neither `getVehicleStatus` nor `getChargingData` validate that the returned data contains the expected structure before persisting. The `{code: 0, message: "success"}` wrapper was stored as `saic-vehicle-status`, and subsequent cached reads return this invalid data instead of fetching fresh data.

**Fix required:** Validate the response structure before persisting:

```typescript
if (data?.basicVehicleStatus) {
  persistVehicleStatus(repo, vin, data);
}
```
