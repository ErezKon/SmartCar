## Phase 1: Enhanced Telemetry

**Status:** Complete  
**Risk:** None (no new API calls, only extracting more data from existing responses)

## Post Implementation Gaps - Fixes

**Status:** Complete  
**Date:** 2026-08-12  
**Context:** All dashboard fields showed "N/A" despite a connected SAIC account and confirmed vehicle. Investigation revealed 4 root causes.

### Root Cause 1 (Critical): Event-ID Polling Terminates Prematurely

**File:** `backend/src/saic/client.ts`

**Problem:** The SAIC API returns an initial `{code: 0, message: "success"}` response WITH an `event-id` header, meaning "poll again for actual data." The client only retried when `code !== 0`, so it returned the wrapper object as if it were vehicle data.

**Fix:** Added a second check after the `code !== 0` block in `singleRequest()`:
```typescript
if (parsed.data === undefined && respEventId) {
  throw new SaicRetryException('Waiting for vehicle data', respEventId);
}
```

This ensures the event-polling loop in `requestWithEventPolling()` continues polling until the API returns actual data in the `data` field.

**Impact:** Fixes ALL signal data — without this fix, no data flows from the API at all.

### Root Cause 2 (High): Charging Telemetry Fields in Wrong JSON Sub-Object

**Files:** `backend/src/saic/types.ts`, `backend/src/saic/normalize.ts`, `backend/src/saic/vehicles.ts`, `backend/src/saic/normalize.spec.ts`

**Problem:** 10 Phase 1 telemetry fields were placed in the `ChrgMgmtData` interface but the API returns them under `rvsChargeStatus`. Additionally, 5 field names were incorrect.

**Fix:**
1. **`types.ts`:** Moved 10 fields from `ChrgMgmtData` to `RvsChargeStatus` with correct API field names:

| Removed from `ChrgMgmtData` | Added to `RvsChargeStatus` (correct name) |
|------------------------------|-------------------------------------------|
| `mileageOfTheDay` | `mileageOfDay` |
| `mileageSinceLastCharge` | `mileageSinceLastCharge` |
| `realtimePower` | `realtimePower` |
| `chargingType` | `chargingType` |
| `chrgngDuration` | `chargingDuration` |
| `powerUsageSinceLastCharge` | `powerUsageSinceLastCharge` |
| `powerUsageOfDay` | `powerUsageOfDay` |
| `chrgngGunState` | `chargingGunState` |
| `lastChargeStartTime` | `startTime` |
| `lastChargeEndTime` | `endTime` |

Note: `bmsChrgSpRsn` correctly remains in `ChrgMgmtData`.

2. **`normalize.ts`:** Updated `normalizeChargingData()` to read affected fields from `data.rvsChargeStatus` (via `rvs` local variable) instead of `data.chrgMgmtData`, using correct field names.

3. **`vehicles.ts`:** Updated `persistChargingSnapshots()` to read from `data.rvsChargeStatus` for the same 8 persisted fields (excluding `startTime`/`endTime` which were never persisted).

4. **`normalize.spec.ts`:** Updated 7 test fixtures to place fields in `rvsChargeStatus` with correct names.

**Impact:** Fixes 8 dashboard signals: `saic-mileage-today`, `saic-mileage-since-charge`, `saic-energy-since-charge`, `saic-energy-today`, `saic-charging-type`, `saic-charging-duration`, `saic-charging-gun-state`, and the `charge-wattage` `realtimePower` path.

### Root Cause 3 (Medium): Silent Error Swallowing in Signals Route

**File:** `backend/src/routes/saic.routes.ts`

**Problem:** Both `getVehicleStatus()` and `getChargingData()` calls in the signals endpoint used `.catch(() => null)` which silently discarded ALL errors — making failures completely invisible.

**Fix:** Added error logging before returning null:
```typescript
getVehicleStatus(vin, refresh).catch((err: Error) => {
  logger.warn(`Failed to get vehicle status for signals: ${err.message}`);
  return null;
}),
getChargingData(vin, refresh).catch((err: Error) => {
  logger.warn(`Failed to get charging data for signals: ${err.message}`);
  return null;
}),
```

**Impact:** Errors are now logged at `warn` level, making debugging failures visible in server logs.

### Root Cause 4 (Low): No Data Validation Before Persistence

**File:** `backend/src/saic/vehicles.ts`

**Problem:** Neither `getVehicleStatus()` nor `getChargingData()` validated that the response contained the expected structure before persisting. Invalid wrapper responses like `{code: 0, message: "success"}` were stored, poisoning the cache.

**Fix:** Added structural validation before persisting:
- Vehicle status: only persists when `data?.basicVehicleStatus` is present
- Charging data: only persists when `data?.chrgMgmtData` is present
- Both log a warning when skipping persistence due to missing data

**Impact:** Prevents stale invalid data from being cached, ensuring cached reads return real vehicle data or trigger a fresh fetch.
