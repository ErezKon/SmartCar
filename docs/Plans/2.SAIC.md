# MG iSmart (SAIC) Direct Integration Plan

Add a self-contained SAIC/MG iSmart provider to the existing `smartcar` app — a TypeScript port of the community reverse-engineered API — with a provider switch in the UI, so an Israeli MG4 account works without Smartcar.

---

## 0. Context & Findings

### Why Smartcar fails
Smartcar brokers MG/SAIC by logging into the iSmart backend on your behalf, and the **country selector picks the SAIC tenant/region context**, not just a locale string. An Israeli iSmart account is provisioned on the regional gateway used by the local MG importer, under a tenant that Smartcar does not offer. Choosing Germany or the Netherlands makes Smartcar authenticate against the EU gateway with the wrong tenant/market context, which surfaces as "wrong credentials".

**Honest assessment: there is no correct country to pick.** Israel is not in Smartcar's supported market list for MG/SAIC. Trying more countries is not a productive use of time. The reverse-engineered API is the right path.

### What SAIC-iSmart-API actually is
> ⚠️ **Network access was unavailable during planning** (no web tooling, shell commands disallowed). The following is from prior knowledge of the project and **must be verified in Sub-Plan A before any code is written.** Every claim below is marked with a confidence level.

Repositories under `github.com/SAIC-iSmart-API`:

| Repo | Role | Confidence |
|---|---|---|
| `saic-python-client-ng` | **Primary reference.** Async Python client for the modern JSON app API. This is what we port. | High |
| `saic-python-client` | Legacy client using ASN.1/UPER binary "MP" protocol over `tap-eu.soimt.com`. Deprecated — **do not port this.** | High |
| `saic-python-mqtt-gateway` | Production consumer of the ng client; best source for polling cadence, rate-limit discipline, field semantics, and command sequencing. | High |
| `reverse-engineering` / docs | Protocol notes, ASN.1 schemas. | Medium |

### Is it "just changing the endpoint"? No.
This is a fundamentally different protocol, not a base-URL swap:

| Concern | Smartcar (current) | SAIC iSmart |
|---|---|---|
| Auth | OAuth 2.0 (client credentials + Connect) | Username/password → bearer token, no OAuth, no consent flow |
| Transport | Plain JSON over HTTPS | JSON **encrypted at the body level** (AES) with custom headers (`tenant-id`, app version, send-date) |
| Read model | Synchronous `GET`, 94 flat signal codes | **Asynchronous event-id polling**: issue request → receive event id → poll until the car answers (the car must wake up) |
| Commands | Synchronous POST | Async, same event-id polling, often requires a PIN/passcode for some actions |
| Multi-session | Designed for it | **Hostile to it.** Logging in via API can invalidate the phone app's session and vice versa |
| Rate limits | Documented, header-driven | Undocumented; aggressive polling drains the 12V battery and can get the account throttled |

Therefore: **new self-contained module inside the existing backend** (per your decision), not a base-URL toggle.

### Confirmed decisions
- **Architecture:** self-contained SAIC module in the existing Express backend — new `/api/saic/*` routes, own client, own DB tables, own UI page(s). No changes to Smartcar code paths.
- **Client:** native TypeScript port using `node:crypto`. No Python runtime, no MQTT broker.
- **Scope:** full parity attempt — telemetry + charging control + lock/unlock + climate/preconditioning + alarm messages.
- **Credentials:** entered via UI, stored encrypted at rest in SQLite, key from `.env`.

### Existing conventions to mirror
- Backend layering: `config/` → `db/` (sql.js + repositories) → `auth/` → `api/` (typed clients) → `routes/` → `middleware/`. Retry/rate-limit logic lives in `api/client.ts`; errors are named classes mapped to friendly messages in `app.ts`.
- Migrations are idempotent `CREATE TABLE IF NOT EXISTS` calls in `db/migrations.ts`.
- Frontend: Angular 17 standalone components, lazy routes in `app.routes.ts`, nav driven by `navItems` in `app.component.ts`, all HTTP via a single service.
- No test infrastructure exists (`npm test` is a stub) — Sub-Plan B introduces the first one.

## Sub-Plan A — Protocol Research & Credential Spike

**Goal:** Produce a complete, verified protocol spec and prove the MG4 account authenticates from this machine. **No application code.**

**Prerequisite:** network access and either shell commands or web tooling must be enabled. This sub-plan cannot be completed without them.

**Read on entry:** this plan file only.

**Tasks**
1. Clone/read `saic-python-client-ng`. Extract and document verbatim:
   - Region → gateway base URL map (expected shape: `https://gateway-mg-<region>.soimt.com`, regions incl. `eu`, `au`, `cn`; **verify exact hostnames and the full region list**).
   - API path prefix (expected `/api.app/v1/`) and tenant id constant.
   - Login request: endpoint, HTTP method, content type (form vs JSON), exact field names, whether the password is hashed or sent plaintext inside the encrypted envelope, and the token/refresh response shape.
   - **Crypto scheme in full detail** — this is the highest-risk item: cipher and mode (expected AES-128-CBC), key derivation, IV derivation, padding, encoding (hex vs base64), which headers participate (`APP-SEND-DATE`, `APP-CONTENT-ENCRYPTED`, `original-content-type`, verification/signature headers), and whether responses are encrypted symmetrically.
   - Required static headers, including the `User-Agent` the app sends.
   - Every endpoint for: vehicle list, vehicle status, charging management data, charging control, lock/unlock, climate/AC, alarm/message list, and the PIN/passcode requirement for each.
   - The async event-id polling contract: initiating header value, how the event id is returned, poll interval, max attempts, and the "not ready yet" vs "real error" response codes.
   - Error/return-code table.
2. From `saic-python-mqtt-gateway`, document operational discipline: poll intervals for active vs idle vehicles, back-off on failure, how it avoids waking the car unnecessarily, and any documented account-lockout hazards.
3. **Region/tenant discovery spike for Israel.** With the user's consent and credentials supplied at runtime (never written to disk or logs), attempt login against each known regional gateway and record which one authenticates. This is the single most important unknown — the whole effort is blocked if no gateway accepts the account. Use a minimal throwaway script; **rate-limit attempts and stop after the first success** to avoid lockout. Delete the script afterwards.
4. Record whether the account has an app-side PIN and which commands require it.

**Deliverable:** `docs/SAIC-PROTOCOL.md` containing all of the above, plus one captured (credential-redacted) request/response pair per endpoint family, and an explicit "Confirmed / Unconfirmed / N/A" table.

**Exit criteria:** the correct gateway for the Israeli account is identified and a successful login is demonstrated. If no gateway works, **stop and report** — do not proceed to B.

**Risks:** repeated failed logins may lock the account; API login may log the phone app out. Warn the user before step 3.

## Sub-Plan B — Crypto & Auth Core

**Goal:** A working TypeScript client that logs in, maintains a token, and performs one authenticated encrypted round-trip.

**Read on entry:** `docs/SAIC-PROTOCOL.md`, `backend/src/api/client.ts`, `backend/src/auth/token-manager.ts`, `backend/src/config/{env,constants}.ts`, `backend/src/db/{database,migrations}.ts`, `backend/src/db/repositories/token.repository.ts`, `backend/src/utils/{errors,helpers,logger}.ts`.

**New files** (all under `backend/src/saic/`):
- `config.ts` — region→gateway map, tenant id, app version, path prefix, poll/back-off constants.
- `crypto.ts` — encrypt/decrypt envelope per the spec, using `node:crypto` only.
- `client.ts` — `SaicClient`: header assembly, body encryption, response decryption, **event-id polling loop**, retry/back-off (reuse `utils/helpers.retry`), typed error mapping.
- `errors.ts` — `SaicApiError`, `SaicAuthError`, `SaicVehicleAsleepError`, `SaicPinRequiredError`.
- `auth.ts` — login, token cache with expiry, refresh-or-relogin, single-flight lock so concurrent requests never trigger parallel logins.
- `credentials.ts` — AES-256-GCM encrypt/decrypt of the stored password using `SAIC_CREDENTIALS_KEY` from `.env`.

**Modified files:**
- `backend/src/config/env.ts` — add `SAIC_CREDENTIALS_KEY`, `SAIC_REGION` (default from Sub-Plan A), `SAIC_POLL_INTERVAL_MS`. Keep the existing non-throwing `getEnvVar(key, false)` style.
- `backend/src/db/migrations.ts` — append tables:
  - `saic_accounts(id, username, password_enc, region, created_at, updated_at)`
  - `saic_tokens(id, account_id, access_token, refresh_token, expires_at, created_at)`
  - `saic_vehicles(vin PRIMARY KEY, account_id, model, name, config_json, updated_at)`
  - `saic_state_snapshots(id, vin, field, value, recorded_at)` + index on `(vin, field)`
  - `saic_command_logs(id, vin, command, status, request_body, response_body, event_id, duration_ms, created_at)` + index on `(vin, created_at)`
  - `saic_messages(id, vin, message_id UNIQUE, type, title, content, message_time, created_at)`
- `backend/src/db/repositories/saic.repository.ts` — repositories mirroring the existing class style.
- `backend/.env.example` — new vars, documented.

**Verification (first test infrastructure in the repo):**
- Add `vitest` as a backend dev dependency (choose a version published ≥7 days ago) and a `test` script.
- `crypto.spec.ts`: round-trip encrypt→decrypt, plus assert against a **known-good vector captured in Sub-Plan A** — this is the only way to prove the port is byte-compatible with the real service.
- `credentials.spec.ts`: encrypt/decrypt round-trip, tamper detection.
- Manual: a temporary script performs login + one authenticated call, then is deleted.
- `npx tsc --noEmit` in `backend/`.

**Risk:** if the known-good vector does not reproduce, everything downstream is blocked. Do not proceed until it passes.

## Sub-Plan C — Telemetry (Read Path)

**Goal:** `/api/saic/*` read endpoints returning normalized vehicle state.

**Read on entry:** `docs/SAIC-PROTOCOL.md`, `backend/src/saic/*`, `backend/src/api/vehicles.ts`, `backend/src/routes/vehicles.routes.ts`, `backend/src/middleware/auth.middleware.ts`, `backend/src/app.ts`.

**New files:**
- `backend/src/saic/types.ts` — response types for vehicle list, status, charging data, messages.
- `backend/src/saic/vehicles.ts` — `listVehicles`, `getVehicleStatus`, `getChargingData`, `getMessages`.
- `backend/src/saic/normalize.ts` — map SAIC fields onto the app's signal-code vocabulary where a genuine equivalent exists (SOC → `tractionbattery-stateofcharge`, range → `tractionbattery-range`, odometer → `odometer-traveleddistance`, GPS → `location-preciselocation`, interior/exterior temp → `climate-*`, doors/locks → `closure-*`, charging flags → `charge-*`, tyre pressures → `diagnostics-tirepressure`). **Do not invent mappings** — SAIC-only fields keep `saic-` prefixed codes and are surfaced as-is.
- `backend/src/routes/saic.routes.ts` — router:
  - `POST /api/saic/account` — save credentials (encrypted), validate by logging in
  - `GET /api/saic/account` — status only, **never returns the password**
  - `DELETE /api/saic/account`
  - `GET /api/saic/vehicles`
  - `GET /api/saic/vehicles/:vin/status` (`?refresh=true` forces a live wake-up poll; default serves the cached snapshot)
  - `GET /api/saic/vehicles/:vin/charging`
  - `GET /api/saic/vehicles/:vin/signals` — normalized view
  - `GET /api/saic/vehicles/:vin/history`
  - `GET /api/saic/messages`

**Modified files:**
- `backend/src/app.ts` — mount `saicRouter` at `/api/saic`; extend the error handler with a `SaicApiError` branch and friendly messages (asleep, PIN required, throttled, bad credentials).

**Design notes:**
- Every fetch writes to `saic_state_snapshots` so the UI has data even when the car is asleep.
- Default to cached reads. Live refresh must be explicit and rate-limited per the cadence documented in Sub-Plan A — protecting the 12V battery is a hard requirement, not a nicety.
- A single in-process poller (opt-in via env) may refresh at the safe interval; off by default.

**Verification:** `tsc --noEmit`; unit tests for `normalize.ts` against fixtures captured in A; live curl of each endpoint against the real car; confirm snapshots persist and the DB file survives restart.

## Sub-Plan D — Commands (Write Path)

**Goal:** Full command set with async result tracking and logging.

**Read on entry:** `docs/SAIC-PROTOCOL.md`, `backend/src/saic/*`, `backend/src/api/commands.ts`, `backend/src/routes/commands.routes.ts`, `backend/src/db/repositories/command-log.repository.ts`.

**New file:** `backend/src/saic/commands.ts` — `startCharging`, `stopCharging`, `setChargeLimit`/`setChargeCurrent`, `lock`, `unlock`, `startClimate`/`stopClimate` (incl. target temperature), `startHeatedSeats` if supported, `findVehicle`/horn-lights if supported.

**Modified:** `backend/src/routes/saic.routes.ts` — `POST /api/saic/vehicles/:vin/commands/:command`, plus `GET /api/saic/vehicles/:vin/commands` for history. Every command writes to `saic_command_logs` with the event id, status, and duration.

**Design notes:**
- Commands are async: submit → poll event id → resolve to success/failure/timeout. Return `202` with a tracking id if the poll exceeds a threshold, and expose a status endpoint.
- Gate PIN-requiring commands behind an explicit, encrypted-at-rest PIN in `saic_accounts`; return `SaicPinRequiredError` if absent.
- Serialize commands per VIN (mutex) — concurrent commands to one car are a known source of failures.
- Guard destructive/physical actions (unlock especially) with clear confirmation semantics in the API contract.

**Verification:** unit tests for payload construction; live tests with the real car, starting with the safest (`findVehicle`, `startCharging`) and only then lock/unlock; verify command logs and that failures produce actionable errors.

**Goal:** Pick the provider in the UI and drive the existing dashboard from either backend.

**Read on entry:** `frontend/src/app/app.component.{ts,html}`, `app.routes.ts`, `core/services/{smartcar-api.service.ts,auth.service.ts}`, `core/models/index.ts`, `features/{dashboard,signals,commands,settings}/*`, `shared/components/*`, plus the `/api/saic/*` contract from C and D.

- `core/models/saic.models.ts` — SAIC response interfaces.
- `features/saic/saic-connect.component.ts` — credential form (username, password, region select, optional PIN), validation feedback, connection status, disconnect.
- `features/saic/saic-dashboard.component.ts` — vehicle state using the existing `signal-card`, `status-badge`, and `command-button` components; live-refresh button with an explicit "this wakes the car" warning; charging panel; message/alarm list.

**Modified files:**
- `app.routes.ts` — lazy routes `/saic/connect`, `/saic/dashboard`.
- `app.component.ts` / `.html` — add a **provider toggle in the toolbar**; filter `navItems` by the active provider so Smartcar-only pages (Webhooks, Compatibility, Connect) hide under SAIC, and SAIC pages hide under Smartcar.
- `features/settings/settings.component.ts` — show which provider is active, the SAIC region, and connection health.
- `features/dashboard/dashboard.component.ts` — read the active provider and source data from the matching service via the normalized signal shape.

4. **Hardening**
   - Audit logs: assert credentials, tokens, PIN, and encryption keys are never logged (the client logs requests at debug level — add a redaction helper and test it).
   - Confirm the SAIC password/PIN never crosses the API back to the browser.
   - Rate-limit the live-refresh and command endpoints server-side.
   - Confirm `helmet` and CORS still apply to the new routes.
   - Verify graceful degradation when the car is asleep or the account is throttled.
5. **Final verification:** backend `tsc --noEmit` + `vitest`, frontend `npm run build`, full Docker up/down, end-to-end run against the real MG4.

## 3. Risks & Considerations

| Risk | Severity | Mitigation |
|---|---|---|
| **No gateway accepts the Israeli account** | Blocker | Sub-Plan A step 3 is a hard gate. Stop and report rather than building on a broken premise. |
| Crypto port not byte-compatible | Blocker | Known-good test vector captured in A; do not leave Sub-Plan B until it passes. |
| Account lockout from repeated failed logins | High | Cap attempts, back off, stop on first success, warn the user before the spike. |
| API login invalidates the phone app session | Medium | Document it. The user should expect to be logged out of iSmart occasionally. |
| Polling drains the 12V battery / wakes the car | Medium | Cached-by-default reads, explicit opt-in for live refresh, cadence copied from the MQTT gateway. |
| Unofficial API changes without notice | Medium | Isolate all protocol knowledge in `src/saic/` behind `config.ts` + `crypto.ts`; document the upstream repos to track. |
| Terms-of-service posture | Low/legal | This accesses the user's own vehicle with the user's own credentials. Note it in `docs/SAIC.md`; not a technical blocker. |
| Feature set narrower than Smartcar's 94 signals | Low | Normalize honestly; never fabricate mappings. The UI hides unavailable signals. |
